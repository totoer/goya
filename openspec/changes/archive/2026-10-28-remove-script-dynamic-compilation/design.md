# Design

## Context

Мотивация описана в `proposal.md`. Текущая реализация имеет три связанных пути входа в frontend во время исполнения:

- `typescript_eval.go` строит `EvalAnalysis`, сохраняет исходный лексический контекст и компилирует IR с текущей VM. `builtin_eval` и инструкции `callEval` вызывают этот путь.
- `builtin_function.go:functionCtor` собирает строку, проверяет параметры и передаёт её `r.eval`; конструктор async-generator из `typescript_async_helpers.go` использует тот же путь.
- `typescript_dynamic.go:compileDynamicModule` обращается к `Analysis.DynamicAnalysis`, который получает новый resolver snapshot, затем выполняет lowering и backend compilation.

Из-за этого `typeScriptProgram` удерживает `*tsfrontend.Analysis`, а frontend содержит eval-specific selection и transform hooks. Сейчас `ExecutionIR` различает только список запускаемых roots и загруженные модули; отдельного разрешённого набора вычисляемых импортов нет. `compileCheckedIR` собирает требования окружения обходом статических зависимостей стартовых roots, поэтому динамический host namespace может не попасть в manifest.

После предыдущего исследования в проект добавлен LSP. `lsp/session.go` вручную копирует `Project` и экспортирует snapshots; новые поля нельзя потерять в этих копиях. Текущие основные спецификации требуют полной поддержки runtime-конструкций и динамической компиляции новых модулей. Delta specs намеренно меняют эти требования; это изменение совместимости, а не только рефакторинг.

## Goals / Non-Goals

**Goals:**

- У runtime нет встроенного пути от строки или неизвестного specifier к новому исполняемому коду.
- `Compile` создаёт автономную программу с подготовленным графом и полным контрактом; resolver и checker не нужны для её исполнения.
- Сохранить полезную семантику функций и модулей, отделив подготовку от инициализации.
- Согласовать одноразовую подготовку с конфигурациями, project references, cache keys и editor snapshots.

**Non-Goals:**

- Новые форматы bytecode/сериализации, hot reload или добавление модулей в существующий `Program`.
- Полный запрет любых Go callback, которые приложение само решило зарегистрировать, либо запрет последовательных вызовов `RunScript` приложением.
- Исправление всех resource-limit проблем или гарантия процессной изоляции.
- Удаление upstream checker или редакторских инструментов, анализирующих и преобразующих исходный текст по запросу Go-приложения.

## Decisions

### 1. Постоянный профиль без динамической компиляции строк

Удалить стандартное глобальное свойство `eval` и его декларацию из используемого профиля стандартной библиотеки. По подтверждённому решению глобальное имя `eval` зарезервировано в типизированном host-реестре: `Registry.Register` отклоняет его явно до проверки деклараций. Методы объектов вроде `api.eval()` допустимы и не получают специальных правил вызова. Обычные лексические ограничения TypeScript strict сохраняются; checker не ослабляется ради одноимённого глобального callback. Удалять всю upstream-библиотеку или запрещать имена свойств по написанию нельзя.

Сохранить объекты `Function` и специализированных конструкторов ради прототипов, `instanceof`, reflection и обычных функций. Их call/construct implementation всегда выбрасывает `EvalError` с сообщением о запрете компиляции строк. Общий guard исполняется до `ValidateFunctionConstructor`, сборки строки и `ToString` аргументов; нормальное вычисление выражений аргументов до вызова сохраняется. Защита находится в intrinsic entry point, поэтому работает через `.constructor`, bound functions, Proxy forwarding и `Reflect.construct`. Все четыре семейства конструкторов покрываются явно.

В `Check`/`Compile` добавить одинаковую goja-диагностику для непосредственно распознанного вызова встроенного конструктора; идентификация основана на разрешённом символе, а не тексте имени. Нет требования статически распознать любой косвенный вызов: runtime guard является обязательной границей. Явный `any`, собственный `.d.ts` или другой `lib` не включают intrinsic обратно. Объявления сохраняют объекты/типы функций, но не обещают доступность генерации кода; profile-specific диагностика поясняет ограничение. Отсутствие встроенного `eval` в стандартных декларациях даёт обычную TypeScript-ошибку имени; обход через `globalThis as any` получает отсутствие значения.

Альтернатива с `AllowEval` отклонена: она сохраняет сложный код, отдельную модель угроз и почти всю стоимость его тестирования. Удаление глобального `Function` без intrinsic guard также отклонено из-за обхода через прототипы и нарушения обычной объектной модели.

### 2. Отдельные startup roots и preparation roots

Добавить `ModuleRoots []string` в `tsfrontend.Project` и тем самым в публичный alias `goja.Project`.

Поле принимает:

- Виртуальный путь source-модуля; в примерах и API-документации использовать абсолютные `/plugins/fast.ts`. Применяется существующая каноникализация виртуальных путей. Допускаются ESM, CommonJS и JSON с соответствующими настройками. `.d.ts` и глобальный script без модульной идентичности не являются исполняемыми module roots; для TS side-effect plugin требуется модульная форма, например `export {}`.
- Точное имя объявленного либо зарегистрированного host-модуля, например `host:api`. Такие записи не требуют source-файла. Двусмысленность между source root и host-именем отклоняется диагностикой. Только наличие ambient declaration разрешает подготовку контракта, но не заменяет startup-проверку реализации.

`ModuleRoots` не добавляет startup roots. Если модуль независимо выбран в `EntryPoints`, он остаётся стартовым; дубликаты канонизируются. Существующий выбор стартовых roots, в том числе configured/empty `EntryPoints`, сохраняется. Для ленивых плагинов приложение задаёт явные `EntryPoints`, чтобы старое правило «все исходники как roots» не запускало их автоматически. Документация показывает именно такой пример.

Подготовленный граф — замыкание стартовых roots и `ModuleRoots` по статическим и строковым динамическим импортам, рекурсивно. Type-only edges дают только проверку типов. Ошибка в любом разрешённом модуле блокирует `Check`/`Compile`; остальные файлы снимка не получают права исполнения просто из-за наличия в `Files` или resolver snapshot. Файл, нужный только для типов, также не получает это право. При configured projects дополнительные roots добавляются к проверяемому графу без изменения списка startup roots и с сохранением project-reference source redirects.

Альтернатива «все Files доступны для импорта» отклонена: каталог может содержать редакторские, тестовые и неразрешённые файлы. Отдельные `Compile` для каждого плагина отклонены как основная модель из-за необходимости связывать разные снимки, контракты и экземпляры модулей во время исполнения.

### 3. Подготовленное разрешение specifier без frontend

Расширить checked IR метаданными startup roots, полного разрешённого графа и подготовленных разрешений. Backend получает их вместе с модульным кодом. Единственный вызов resolver для конкретного анализа остаётся на этапе получения project snapshot; подготовка не начинает повторно запрашивать изменяемый resolver для динамических целей.

Для строковых импортов сохранить точные решения checker по `(importer, specifier, resolution mode)` и канонические target IDs. Для вычисляемых импортов подготовить конечный каталог допустимых aliases к разрешённым targets: относительные/абсолютные виртуальные пути с применимыми TS/output extensions, host-имена, package aliases, `paths` и reference redirects. Использовать те же правила и приоритеты resolution, что и во время подготовки. Wildcard aliases разворачивать только относительно конечного подготовленного набора; неоднозначность разрешает существующий compile-time resolver, а не произвольный порядок map.

Допускается компактное представление нормализованных path rules вместо полного декартова произведения importer/alias, но runtime lookup не получает исходники, конфигурационные JSON, package manifests, frontend program или callback resolver. Его результат всегда пересекается с разрешённым набором текущего `Program`. Неизвестный bare specifier не считается host-модулем по умолчанию. Namespace, оставшийся от другой программы в том же runtime, не даёт права импортировать его из текущей программы.

Существующие правила import attributes, JSON types, extension rewriting, ESM/CJS resolution modes и reference redirects проверяются при подготовке и там, где значения attributes динамические, при исполнении. Неподдерживаемые attributes по-прежнему отклоняются. URL не становится загрузчиком: только явно подготовленный виртуальный/host alias способен разрешиться; специально поддерживать `data:` как исходник запрещено.

Идентичность кешируемого модуля включает его подготовленный каталог и нормализованные правила импортов. Иначе одна и та же функция загрузчика могла бы переиспользоваться другой программой с разрешениями исходной программы. Несовместимый уже загруженный модуль блокирует запуск до пользовательских эффектов, включая запуск обычного script с дополнительными roots. Модули без динамических импортов сохраняют прежнее разделение идентичности от несвязанных файлов и порядка стартовых точек.

Альтернатива «сохранить Analysis и разрешать только по старому snapshot» отклонена: она оставляет тяжёлую зависимость runtime от frontend и возможность незаметно вернуться к компиляции во время исполнения.

### 4. Динамический импорт меняет выбор цели, сохраняя module lifecycle

В `typescript_dynamic.go` заменить `compileDynamicModule` на lookup подготовленного target. Выполнять lookup и завершение импорта в существующем promise-job протоколе; не превращать подготовленный `import()` в синхронный возврат namespace.

Для source target передавать подготовленные units существующему linker/evaluator: инстанцирование, SCC/async initialization, cycles и failure caching сохраняются. Для host target использовать namespace только после общего preflight. Неизвестный вычисляемый target даёт rejected Promise с `TypeError`; известный строковый неразрешимый импорт уже блокирует подготовку. Повторные и конкурентные импорты разделяют один экземпляр. Сохраняются thenable namespace assimilation, deferred namespaces и существующая модель CommonJS.

Пустой `ModuleRoots` не отключает литеральные динамические импорты: они замыкаются автоматически. Вычисляемый импорт может выбирать любой доступный alias уже включённого target, в том числе статической зависимости. Ошибки выполнения подготовленного модуля остаются обычными ошибками исполнения, а не ошибками компиляции.

### 5. Preflight проверяет весь разрешённый граф

Собирать manifest globals/host modules со всех подготовленных units, а не только по статическим рёбрам startup roots. Для динамического host namespace консервативно фиксировать полный экспортируемый контракт; динамический выбор свойства не позволяет сузить его до нескольких экспортов. Для чисто статического именованного импорта существующее сужение требований сохраняется. `ModuleRoots` host entry требует namespace-контракт аналогично `import()`.

`RunProgram` проверяет этот manifest до пользовательских инициализаторов, включая стартовые побочные эффекты инициализации модулей. Независимые дополнительные регистрации окружения разрешены, но не включаются в prepared import catalog автоматически. Контракт берётся из исходной компиляции и не перестраивается под runtime environment.

Это намеренно более ранний отказ: неиспользованный в конкретном запуске плагин с отсутствующим host API блокирует запуск всего пакета. Альтернатива проверки в момент `import()` отклонена, поскольку тогда часть эффектов стартовой программы уже могла произойти. Приложение, которому нужны разные полномочия, компилирует разные наборы.

### 6. Исполняемая программа не удерживает frontend

После передачи units, frozen resolution catalog, hashes/profile, manifest и исходных позиций убрать `typeScriptProgram.analysis`, eval origin/base и resolver-bearing данные. `Program` продолжает хранить необходимые исходные тексты/позиции для стеков и `Function.prototype.toString`; это не требование удалить любые строки исходников из памяти. Бounded compilation cache и LSP вправе удерживать Analysis по своим существующим правилам, независимо от времени жизни runtime.

Удалить production `EvalAnalysis`, `DynamicAnalysis`, eval-specific transform resolver/selection, `ValidateFunctionConstructor` и VM/compiler ветки, нужные только direct eval. Не удалять общие механизмы lexical environments, dynamic objects и других поддерживаемых конструкций лишь из-за исторических eval-комментариев.

Исторический `vmFixtureEvaluator` существует только ради старых VM-тестов. Он не должен оставлять скрытый production evaluator. Eval-зависимые fixtures либо переводятся в явно отдельный test-only harness без восстановления intrinsic в проверяемом runtime, либо заменяются/помечаются как неподдерживаемые в профиле. Публичные проверки нового запрета никогда не используют такой harness. Вендорный upstream frontend и его общие editor/refactor операции не удаляются.

### 7. Идентичность подготовки и редакторский контекст

Cache key включает нормализованные `ModuleRoots`, startup roots и новую версию профиля наряду с существующими files/options/config graph/Environment. Порядок и дубликаты `ModuleRoots` не меняют набор разрешений. Изменение хотя бы набора целей не использует старый compiled import catalog.

В `lsp/session.go`, snapshots, project clone helpers и editor adapters копировать новое поле без aliasing; экспортированный проект должен воспроизводить разрешённый набор при `Check`/`Compile`. Использовать общий профиль стандартных объявлений и одинаковую диагностику однозначных forbidden intrinsic calls в компиляции и редакторском анализе. Редактор может продолжать анализировать незавершённый исходник; это не предоставляет runtime возможность компиляции.

Правки профиля оформлять в owned overlay/normalizer и воспроизводимых inventory/import tools, не случайными ручными изменениями vendored TypeScript assets. Обновить compatibility/runtime fixture inventory: eval/function-constructor строка становится явным ограничением профиля; отсутствие её fixtures нельзя выдавать за полную ECMAScript совместимость.

## Risks / Trade-offs

- [Библиотеки используют `new Function` или `eval`] -> Breaking change документируется; миграция на заранее написанные функции, таблицы dispatch или host-компиляцию.
- [Плагины нужно проверять заранее, даже если ветка не выбрана] -> Явные `ModuleRoots`, отдельные программы для разных наборов и ранние диагностики.
- [Подготовка и код занимают больше времени/памяти до запуска] -> Компилировать только разрешённое замыкание; исключить повторный frontend и удержание Analysis самим Program. Измерить на пакете с несколькими ленивыми модулями.
- [Сложные `paths`/exports/references дают другой computed target] -> Общие compile-time правила, frozen decisions и сравнительные тесты строкового/вычисляемого импорта, включая конфликтующие aliases и разные importer directories.
- [Удаление eval ломает исторические tests и optimisation assumptions] -> Разделить test-only legacy fixtures и публичный профиль; проверить положительные случаи closures, arguments, this, private fields, async/generator, `call`/`apply`/`bind`.
- [Go callback намеренно заново компилирует код] -> Это явная возможность приложения; запрет относится к встроенным механизмам скрипта, а не полномочиям владельца Go API.
- [Без eval сохраняются regexp/BigInt/OOM риски] -> Документация не объявляет новую модель полноценной sandbox или заменой процессным лимитам.

## Migration Plan

1. Ввести preparation metadata, `ModuleRoots`, профиль и тесты контракта; изменения готовятся одним согласованным релизом, без промежуточного публичного режима совместимости.
2. Перевести dynamic import на prepared catalog, обеспечить полный preflight, затем удалить eval/frontend зависимости из runtime и связанные production special cases.
3. Заменить тесты свежих resolver snapshots и успешного eval проверками запрета и заранее подготовленных плагинов; обновить LSP/project snapshots и документацию.
4. Приложения перечисляют вычисляемые цели в `ModuleRoots`, сохраняют явные `EntryPoints`, предоставляют все требуемые host-контракты и компилируют новый `Program` при обновлении исходников.
5. Выполнить обязательные проверки проекта и targeted regression/race tests. Откат — возврат предыдущего релиза библиотеки целиком; persisted bytecode и миграции данных не вводятся. Настройки временного возврата eval в новом профиле нет.
