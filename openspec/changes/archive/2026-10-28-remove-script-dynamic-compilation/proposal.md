# Proposal

## Why

Выполняемый скрипт сейчас может повторно запускать frontend через `eval`, конструкторы функций и динамический импорт новых исходников. Эти пути усложняют проверку окружения, отмену и лексическую семантику; проекту нужна единая граница: исходники загружает и компилирует Go-приложение, runtime исполняет подготовленный код.

## What Changes

- **BREAKING** Удалить встроенный `eval` и возможность компиляции строк через любые конструкторы функций, включая доступ через прототипы и алиасы. Настройки повторного включения не будет.
- **BREAKING** Сохранить `import()`, но разрешить ему только модули из неизменяемого набора, подготовленного `Compile`. Runtime больше не получает свежие снимки resolver и не вызывает checker/lowering.
- Добавить `Project.ModuleRoots`: дополнительные модули, разрешённые Go-приложением для вычисляемых импортов; отделить их подготовку от запуска `EntryPoints`. Статические и строковые динамические зависимости включать автоматически.
- Подготовить разрешение импортов, исходные идентичности и требования host API заранее. Неизвестный вычисляемый импорт отклоняет Promise без загрузки исходников; несовместимые привязки всего разрешённого графа блокируют запуск.
- Сохранить семантику асинхронного импорта, циклов, live bindings, CommonJS interoperability, import attributes, deferred evaluation и однократной инициализации подготовленных модулей.
- Согласовать стандартные объявления, `Check`/`Compile`, редакторские snapshots, документацию и compatibility inventory с новым профилем. Удалить удержание frontend Analysis из исполняемой программы после переноса нужных метаданных.
- Сохранить компиляцию из Go API (`Check`, `Compile`, `RunString`, `RunScript`). Новые версии модулей требуют новой компиляции; расширение набора внутри действующего `Program` не входит в изменение.

## Capabilities

### New Capabilities

Нет: поведение относится к существующим возможностям исполнения, компиляции, модулей и host API.

### Modified Capabilities

- `pure-go-execution`: профиль без встроенной компиляции строк и загрузки новых исходников из скрипта; явная граница совместимости языка.
- `typescript-compilation`: подготовка дополнительных module roots, согласованные проверки профиля и идентичность неизменяемой программы.
- `typescript-modules`: предварительно подготовленный граф вместо динамической компиляции, фиксированное разрешение импортов и сохранение исходных идентичностей referenced projects.
- `typed-host-api`: предварительная проверка контрактов всех разрешённых модулей, включая динамические, до любых пользовательских инициализаторов.

## Impact

Затрагиваются `Project`, frontend configuration/cache/IR, `typescript_compile.go`, `typescript_dynamic.go`, `typescript_eval.go`, конструкторы функций, VM/compiler eval-special cases и module linker. В `lsp/session.go` и editor adapters нужно сохранить новые параметры проекта и общий профиль объявлений. Изменятся тесты динамической загрузки, eval/function constructors, legacy VM fixtures, conformance exclusions и документация в `README.md`/`docs/typescript-*.md`.

Программы с генерацией кода из строк и загрузкой новых модулей после запуска потребуют миграции. Новых внешних зависимостей не требуется. Исправление удержания host-объектов, regexp/BigInt resource limits и процессная изоляция остаются отдельными изменениями; host-приложение само отвечает за возможности явно зарегистрированных callback-функций.
