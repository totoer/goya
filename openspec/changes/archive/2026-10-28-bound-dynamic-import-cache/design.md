# Design

## Context

Мотивация описана в `proposal.md`. `typescript_dynamic.go` и fallback `module_commonjs.go` напрямую читают и пополняют общую `Runtime.dynamicResolutions map[string]string`. Ключ склеивает `analysisKey`, исходный модуль и ненормализованный specifier; native import добавляет deferred-режим и сериализованные attributes. `LookupPreparedImport` уже нормализует виртуальные пути через `PreparedSpecifierKey`, но кэш делает поиск до этого шага.

`moduleInstances` отдельно хранит канонические экземпляры, состояние асинхронной оценки, ошибки и namespace. Совместимость кода и разрешений проверяется fingerprint, включающим подготовленные imports/rules. Замороженные wildcard-правила могут сопоставлять бесконечно много имён одному файлу. В `internal/tsfrontend/cache.go` уже есть пример LRU с ограничениями количества и размера; runtime-кэш не должен зависеть от его глобального состояния или блокировок.

Дизайн необходим из-за изменения общей структуры данных и влияния промахов на несколько протоколов загрузки.

## Goals / Non-Goals

**Goals:**
- Ограничить удерживаемые вспомогательным кэшем строки и служебные записи независимо от количества импортов, написаний и выполненных программ.
- Сохранить быстрый путь повторного импорта и одинаковую нормализацию с подготовленным каталогом.
- Проверять ограничения детерминированно по внутренним данным, без зависимости от GC и измерения общей heap.

**Non-Goals:**
- Ограничение общего состояния runtime, количества канонических экземпляров или памяти незавершённых promise jobs.
- Изменение разрешения модулей, frontend, fingerprints, публичных API или потоковой модели runtime.
- Сведение всех разных aliases и расширений одного target к одному ключу: для таких имён достаточно общего конечного бюджета.

## Decisions

### 1. Общий составной ключ с нормализацией только виртуального пути

В новом внутреннем помощнике, например `module_resolution_cache.go`, определить сравнимый ключ с полями: analysis identity, исходный module ID, результат `PreparedSpecifierKey(from, specifier)`, режим native/deferred/CommonJS и детерминированное представление attributes. Оба загрузчика используют общий конструктор ключа и операции кэша. Режимы имеют отдельные значения, чтобы различающиеся протоколы не разделяли записи случайно.

Исходный specifier остаётся аргументом подготовленного lookup и текстом диагностик. Порядок преобразования аргументов, чтения getters attributes и постановки promise job не меняется. При отсутствии подготовленной программы сохраняется существующая ошибка; пустой общий ключ не создаётся.

Альтернатива с произвольным `path.Clean` опасна: bare aliases и package specifiers должны сохранять точное значение и блокировки. Ключ только по target потребовал бы сначала выполнять lookup при каждом импорте и менять текущий быстрый путь. Составной ключ также исключает неоднозначность склеивания произвольных строк разделителями.

### 2. Один лениво создаваемый LRU на runtime

Заменить прямую map обёрткой над map и `container/list`. Запись хранит ключ, канонический target (включая существующее представление host-target) и рассчитанный размер. Успешный lookup переносит запись в начало LRU. Сохранение существующего ключа обновляет ту же запись и корректирует счётчик; удаление освобождает ссылки и в map, и в списке.

Предлагаемые внутренние значения по умолчанию: **256 записей и 64 KiB строк на runtime**. Это начальные параметры реализации, а не публичный контракт; спецификация требует конечных лимитов. Тесты помощника могут задавать малые лимиты без глобальных настроек и публичного setter.

Размер записи равен сумме длин всех строковых полей ключа и target в байтах. При сохранении учитывать владение строками: короткая подстрока не должна удерживать большое исходное backing storage; при необходимости копировать сохраняемые поля. Служебные структуры ограничены числом записей; byte budget не объявляется точной оценкой всей Go heap.

Запись, которая сама превышает byte budget, не сохраняется и не вытесняет полезные записи. Для остальных вставок вытеснять самые старые до соблюдения обоих лимитов. Нулевые внутренние лимиты отключают удержание. Бюджет общий для всех программ и обоих загрузчиков в данном runtime; отдельный кэш на программу позволил бы обойти runtime-границу.

Только ограничение числа записей оставляет возможность удержать очень длинные строки. Только канонизация не ограничивает wildcard-алиасы. Полный отказ от кэша проще, но убирает существующий быстрый путь всех повторных импортов. Полная очистка при переполнении дешевле по коду, но приводит к одновременной потере часто используемых записей; выбран LRU.

### 3. Вытеснение не управляет жизненным циклом модуля

Кэш хранит только разрешение в канонический ID. Промах, отсутствие target в `moduleInstances` или пропуск сохранения следуют существующему пути: prepared lookup, применимые проверки attributes/async graph/preflight и запуск подготовленного графа. Сохранять разрешение в тех же точках, где сегодня подтверждён host-target либо совместимый fingerprint экземпляра, в том числе экземпляра с сохранённой ошибкой выполнения. Не добавлять отрицательное кэширование неизвестных импортов.

Вытеснение не трогает `moduleInstances`, namespace, live bindings, evaluation promise, failure, interruption и deferred namespace. Новые разрешения не обходят проверки другой программы. При промахе должны сохраняться существующие запреты несовместимого кода и незарегистрированных host-модулей. Синхронный CommonJS-путь сохраняет отказ от async-графа и свою форму exports/JSON-значений.

### 4. Проверки границ и семантики

Добавить внутренние тесты помощника и интеграционные регрессии в package `goya`, чтобы проверять число записей, сумму строк и реальные экземпляры без публичной диагностики кэша. Существующие внешние тесты в `typescript_dynamic_test.go`, `typescript_prepared_test.go` и `typescript_json_test.go` остаются проверками совместимости.

Проверять отдельно ESM и CommonJS, а также их совместное использование в одном runtime. Серии эквивалентных путей должны давать одну запись на контекст/режим. Для `paths` с фиксированным target использовать больше различных wildcard-алиасов, чем лимит, включая одиночный oversized alias. После реального вытеснения проверять namespace/live bindings, одно выполнение инициализатора, ожидающий top-level await, сохранённую ошибку, JSON attributes и deferred-режим. При тестировании CommonJS сравнивать идентичность канонического экземпляра/exports: трансформер может создавать внешнюю interop-обёртку namespace.

## Risks / Trade-offs

- Дополнительные промахи увеличивают работу с подготовленным каталогом и preflight → сохранить LRU и проверить, что повторяющийся горячий импорт остаётся попаданием.
- Расхождение нормализации между загрузчиками → общий конструктор с существующим `PreparedSpecifierKey` и тесты обоих входов.
- Ошибка счётчика или удержание удалённой строки → проверки замены, вытеснения, oversized-записей и полного состава map/list после операций.
- Ограничение только этого кэша не ограничивает всю память runtime → проверять отдельно вспомогательное удержание и число экземпляров; не обещать общий memory limit.
- После вытеснения вновь выполняются существующие проверки совместимости → сохранить их порядок и покрыть изоляцию permissions, attributes и async/deferred-протоколы.

## Migration Plan

Изменение внутреннее, миграция данных и конфигурации не требуется: новый кэш создаётся при первом использовании runtime. Для отката достаточно вернуть прежнюю реализацию; форматы подготовленной программы, внешние API и идентичности модулей не меняются.
