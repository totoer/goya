# Proposal

## Why

Runtime сохраняет каждое исходное написание динамического specifier в неограниченной `dynamicResolutions`, хотя экземпляр модуля уже имеет каноническую идентичность. Поэтому даже один подготовленный модуль позволяет накапливать память через эквивалентные пути и wildcard-алиасы; проблема затрагивает также `import()`, преобразованный в CommonJS.

## What Changes

- Канонизировать виртуальные пути в ключах общего вспомогательного кэша тем же `PreparedSpecifierKey`, который использует подготовленный lookup; сохранить точное написание bare aliases и package specifiers.
- Ограничить кэш каждого runtime одновременно числом записей и суммарным размером сохраняемых строк, с LRU-вытеснением и пропуском слишком больших записей.
- Применить общие операции построения ключа, поиска и сохранения к ESM `import()` и CommonJS fallback в `requireModule`.
- Сохранить контекст программы и импортирующего модуля, проверки attributes, deferred-режим, разрешения импортов и состояние канонических экземпляров при попадании, промахе и вытеснении.
- Добавить регрессии для вариантов путей, бесконечного множества wildcard-алиасов одного модуля, длинных ключей и повторного импорта после вытеснения.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `typescript-modules`: ограниченное удержание вспомогательных разрешений динамических импортов, канонизация эквивалентных виртуальных путей и сохранение существующих протоколов после вытеснения.

## Impact

Затрагиваются `runtime.go`, `typescript_dynamic.go`, `module_commonjs.go`, новый внутренний помощник кэша и тесты модулей. Используется существующий `internal/tsfrontend.PreparedSpecifierKey`; новые зависимости и публичные API не требуются. Основной кэш `moduleInstances`, подготовленные каталоги, компиляционный кэш и правила разрешения модулей остаются вне области изменения. При вытеснении увеличивается число обращений к замороженному каталогу, но импорты продолжают работать без resolver и компиляции во время исполнения.
