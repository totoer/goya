# Design

## Context

Мотивация описана в `proposal.md`; контракт добавляется в `specs/typed-host-api/spec.md`.

Сейчас `Runtime.hostViews` индексирует `*Object` ключом из сильного Go-указателя и `viewSchema`, а `hostViewSources` хранит обратное соответствие `*Object -> reflect.Value`. Обе таблицы живут до сборки runtime. `hostConversion.objectMembers` создаёт обычный объект с живыми accessor-полями и привязанными методами. Getters, setters, native-функции и создаваемые через `reflect.MakeFunc` callbacks захватывают `c`, включая временные `inputs` и `outputs`.

`host_struct_test.go` и `host_cycles_test.go` уже требуют идентичность между зарегистрированным объектом, возвращённым указателем и рекурсивным полем, а также восстановление исходного указателя на входе. `docs/typescript-embedding.md` обещает views для pointer-to-struct, копии коллекций, readonly по умолчанию и изоляцию runtime. Текущая основная спецификация `typed-host-api` не определяет время жизни views; новые требования дополняют её без изменения существующих требований.

Проект использует Go 1.27, `weak.Pointer` и `runtime.AddCleanup`. В `shared_array_buffer.go` уже есть слабый индекс, очищаемый при создании объектов. Для этой задачи одной такой очистки недостаточно: после последнего вызова runtime может долго простаивать. `builtin_finalization_registry.go` показывает применение cleanup без исполнения VM из фоновой goroutine; пользовательская очередь финализации не подходит для удаления записей, поскольку зависит от `RunJobs`.

## Goals / Non-Goals

**Goals:**

- Устранить сильные пути от индекса к view и Go source, сохранив существующее преобразование, доступ к полям и типовую идентичность.
- Разделить владение данными, учёт идентичности и краткоживущее состояние конверсии.
- Сделать фоновое удаление записей безопасным и независимым от активности VM.
- Проверять собираемость самих объектов и связанных данных, а также удаление записей, без привязки к точному расходу RSS.

**Non-Goals:**

- Детерминированный release, отзыв живых views, закрытие внешних ресурсов и новый публичный lifecycle API.
- Изменение правил копирования структур/коллекций, TS-деклараций, numeric policies, схем контрактов или поведения пользовательских `HostAdapter`.
- Потокобезопасность runtime в целом: синхронизация охватывает только закрытый индекс, к которому обращается cleanup.

## Decisions

### 1. Source принадлежит закрытому представлению host view

Ввести специализированную внутреннюю реализацию объекта, встраивающую `baseObject` и хранящую исходный pointer `reflect.Value`. Публичный `*Object` остаётся прежним. На входе bridge распознаёт эту реализацию после существующей проверки принадлежности runtime и возвращает source при точном совпадении Go-типа. Удалить `hostViewSources` из runtime.

Сохранять именно снимок значения указателя, например `reflect.ValueOf(value.Interface())`, а не адресуемый `reflect.Value` поля, которое host может позже переназначить. View продолжает представлять первоначальный receiver. Такое владение сохраняет указатель и для структур без доступных полей/методов.

Внутренние source и identity не являются JS-свойствами и не влияют на обычный export, прототип, перечисление, дескрипторы или разрешения. Getters и методы сохраняют только необходимые receiver/данные, поэтому извлечённый метод продолжает работать после сборки объекта view.

Альтернативы: дополнительное поле у каждого `Object` увеличивает размер всех объектов; обратная таблица со слабыми ключами и сильными sources создаёт второй индекс и риск удержания через циклы; одни accessor-замыкания не сохраняют source для объектов без членов. Специализированная реализация локализует изменение.

### 2. Отдельный слабый индекс идентичности

Runtime хранит указатель на закрытый cache с mutex и map. Ключ состоит из точного `reflect.Type` указателя, его числового адреса `uintptr` и существующей `viewSchema`; значение — `weak.Pointer[Object]`. Ключ не содержит `any` с Go-указателем, `unsafe.Pointer`, source или view. Числовой адрес используется исключительно для сравнения и никогда не преобразуется обратно в Go-указатель.

На lookup сильная ссылка получается одним вызовом `Value()` и сохраняется локально. Живой view сам удерживает source, поэтому адрес source не может быть переиспользован для другой аллокации, пока этот view доступен. Если слабая ссылка пуста, запись допускает замену новым view. Точный Go-тип разделяет указатели разных типов, а `viewSchema` разделяет контракты, включая mutability и mapper. Для zero-sized Go-значений сохраняется существующая семантика сравнения Go-указателей; новая уникальность отдельных zero-sized аллокаций не обещается.

```text
Runtime --> cache --weak--> host view --> source
Go/TS roots -------------> host view
cleanup --> cache
```

Cache не хранит обратной сильной ссылки на runtime или объекты. Синхронизация охватывает lookup, публикацию, замену и удаление. Конверсию, создание свойств и вызов пользовательского кода выполнять вне mutex. Не публиковать успешно возвращаемое представление до завершения инициализации; при ошибке удалить возможную промежуточную запись только при совпадении её identity.

Альтернативы: слабое значение при прежнем ключе сохраняет source; слабый ключ при сильном значении сохраняет view и через него source; сброс после запуска или LRU нарушают идентичность сохранённых views. Слабые ключи произвольных reflect-типов потребовали бы отдельного стирания типа указателя; числовой ключ избегает такого механизма и не используется для разыменования.

### 3. Cleanup удаляет только свою запись

Для каждого view зарегистрировать `runtime.AddCleanup` на публичном объекте. Аргумент cleanup содержит только cache, ключ и слабую identity этого view. Он не содержит `Runtime`, `hostConversion`, source, receiver или сильную ссылку на объект. Cache также не даёт сильного пути к target, поэтому сам аргумент cleanup не удерживает target даже косвенно.

Cleanup берёт mutex и удаляет запись, только если её текущее слабое значение совпадает с переданной identity. Сравнение weak-токенов отличает собранный объект от нового даже при повторном использовании адреса. Запоздалый cleanup старого view не может удалить его замену. При опустошении map освободить её backing storage, заменив на nil; следующая вставка создаёт map заново. Очищать найденную мёртвую запись можно также при lookup, но это не является единственным механизмом удаления.

Фоновая функция не входит в VM, не трогает globals, методы объектов или пользовательскую очередь finalization и не запускает callbacks. Сильные локальные ссылки и `runtime.KeepAlive` защищают target/source до завершения регистрации и публикации, где это требуется анализом достижимости.

`AddCleanup` выбран вместо `SetFinalizer`: у объектов и `baseObject.val` есть циклы; cleanup допускает сборку циклов. Тайминг не обещается, один `runtime.GC()` не является барьером завершения cleanup. Даже до удаления записи слабый индекс уже не удерживает source или view.

### 4. Постоянные замыкания не захватывают контекст конверсии

В `function`, `objectMembers` и ветке `input` для `reflect.Func` явно отделить захватываемые runtime/type graph, типовую ноду, callable и receiver от `hostConversion`. Каждое фактическое обращение по-прежнему создаёт новый контекст для input/output и сохранения циклов в пределах одной конверсии.

Не обнулять карты посреди конверсии: несколько аргументов, результатов и рекурсивные коллекции используют общие memo-таблицы. Освобождение достигается отсутствием внешних захватов контекста, а не изменением семантики его обработки. Go-функция или JS-callback могут намеренно удерживать receiver и собственные captures; это допустимое владение, которое bridge не отменяет.

### 5. Проверки достижимости и гонок

Добавить внутренние lifecycle-тесты для доступа к закрытому cache и внешние поведенческие проверки там, где уже проверяется host API. GC-сценарии создавать вспомогательными функциями, возвращающими только слабые наблюдатели; runtime оставлять живым через `runtime.KeepAlive`. Использовать нетривиальные heap-объекты и отдельные payload, чтобы не зависеть от tiny allocation и случайно живых локальных переменных.

Основная регрессия: 1000 новых указателей с независимыми Go payload, отброшенные результаты, повторные GC с ограниченным ожиданием cleanup, отсутствие сильных ссылок на views/payload и возврат числа записей индекса к исходному. После генерации результатов не запускать VM, не создавать views и не вызывать `RunJobs`. Проверка живого view должна одновременно подтверждать сохранность source и идентичность после GC.

Отдельно проверить: рекурсивные и смешанные Go/JS циклы; source без доступных членов; замену поля-указателя; readonly/mutable и mapper-контракты; разные Go-типы с одинаковым адресом и схемой; разные runtime; извлечённые методы; входные callbacks и возвращённые функции; независимые аргументы и соседние результаты. Оставшиеся сильные ссылки host-приложения должны сохранять свои данные.

Запоздалое удаление проверять детерминированно на операции условного удаления индекса, подставляя старую weak identity после установки новой; не ждать случайного повторного использования адреса. Повторные серии создания/сборки и `go test -race` проверяют совместную работу cleanup и новых конверсий без конкурентного использования VM пользователем.

## Risks / Trade-offs

- Недетерминированный GC и cleanup могут сделать тесты нестабильными -> ограниченное ожидание с повторным GC, слабые наблюдатели, явное удержание только проверяемых корней; без требования завершения за один GC.
- Захват runtime/source в аргументе cleanup вернёт удержание -> минимальный аргумент, отдельный cache без обратных сильных ссылок и регрессия на сборку самого runtime после удаления внешних корней.
- Старый cleanup может совпасть по числовому ключу с новым view -> сравнивать полную weak identity перед удалением под mutex.
- Специализированный объект может затронуть поведение обычных объектов -> сохранить `baseObject`-операции и существующие проверки прототипа, полей, методов, export, readonly/mutable и рекурсивности.
- Mutex и cleanup на каждый view добавляют накладные расходы -> критические секции ограничены map-операциями; исключить полный проход по всем записям при каждом создании.
- Go allocator может сохранять освобождённые страницы, а у непустой map возможна ёмкость после пика -> проверять достижимость payload и удаление записей; не обещать немедленное уменьшение RSS. Пустая map освобождается.

## Migration Plan

Изменение применяется к новым экземплярам runtime после обновления библиотеки; миграция сохранённых данных и перекомпиляция программ не нужны, поскольку TypeScript-контракты и их схемы не меняются. Обновить документацию одновременно с реализацией. Откат возможен обычным возвратом версии библиотеки и восстановит прежнее удержание views; пользовательские данные и форматы не изменяются.
