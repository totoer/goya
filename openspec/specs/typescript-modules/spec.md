# typescript-modules Specification

## Purpose

Определяет проверку и выполнение TypeScript-модулей с разрешением исходников и внешних зависимостей, контролируемым встраивающим Go-приложением.

## Requirements

### Requirement: Application controlled module resolution
Разрешение исходников, объявлений и host-модулей MUST использовать снимок и правила Go-приложения при подготовке программы. Runtime MUST использовать только подготовленные разрешения и идентичности модулей, без повторного вызова resolver, чтения исходников или обращения к frontend. Неявные обращения к файловой системе, сети или Node.js package loader MUST отсутствовать.

#### Scenario: In-memory project
- **WHEN** приложение предоставляет точку входа и зависимости из памяти
- **THEN** проект проверяется, компилируется и выполняется без чтения пользовательских модулей с диска

#### Scenario: Unresolved dependency
- **WHEN** статический импорт не разрешён приложением и не является встроенным объявлением языка
- **THEN** компилятор возвращает ошибку разрешения и не выполняет проект

#### Scenario: TypeScript output-style specifier
- **WHEN** resolver приложения сопоставляет `./util.js` с исходником `util.ts` по правилам выбранной конфигурации TypeScript
- **THEN** checker и runtime используют один TS-модуль без требования загружать JavaScript-файл

#### Scenario: Resolver is unavailable during execution
- **WHEN** после компиляции приложение делает resolver недоступным, а скрипт импортирует подготовленный модуль
- **THEN** импорт выполняется без нового вызова resolver и использует замороженные правила разрешения

### Requirement: Static dependency checking
До создания исполняемой программы система MUST проверить граф статических и строковых динамических зависимостей точек входа и дополнительных module roots, включая применимые `.d.ts`, из одного снимка. Type-only imports MUST участвовать в проверке и MUST NOT создавать исполняемую зависимость. Наличие файла только в каталоге MUST NOT само разрешать его вычисляемый импорт.

#### Scenario: Invalid imported type
- **WHEN** импортированный тип приводит к несовместимому присваиванию в другом модуле
- **THEN** компиляция возвращает ошибку типов до выполнения любого модуля

#### Scenario: Declaration-only dependency
- **WHEN** модуль импортирует только тип через `import type`
- **THEN** тип доступен checker, а runtime не требует исполняемой реализации этой зависимости

#### Scenario: Invalid literal dynamic dependency
- **WHEN** исходник содержит `import("./plugin.js")`, а соответствующий модуль содержит ошибку типов
- **THEN** `Check` и `Compile` возвращают ошибку до создания исполняемой программы

#### Scenario: Catalog is not an execution grant
- **WHEN** файл не входит в стартовый граф, граф строковых динамических импортов или `ModuleRoots` и присутствует только в снимке исходников
- **THEN** вычисляемый импорт этого файла отклоняется без его компиляции и выполнения

### Requirement: TypeScript module execution semantics
Система MUST исполнять модульные конструкции поддерживаемого TypeScript, включая ESM, export assignment и import assignment, с согласованной семантикой выбранных настроек. Она SHALL поддерживать циклы, live bindings, однократную инициализацию на runtime и top-level await без подключения Node.js.

#### Scenario: Cyclic live bindings
- **WHEN** два TS-модуля циклически импортируют изменяемые экспорты
- **THEN** значения, порядок инициализации и ошибки доступа до инициализации соответствуют семантике модулей, без копирования экспорта как снимка

#### Scenario: Asynchronous module initialization
- **WHEN** модуль использует top-level await и импортируется зависимым модулем
- **THEN** зависимый модуль ожидает завершения необходимой инициализации и получает её результат либо ошибку

### Requirement: Checked dynamic imports
`import()` MUST выбирать только заранее подготовленные source/JSON/host-модули по замороженным правилам программы. Он MUST NOT проверять или компилировать новый исходник. Неизвестный вычисляемый импорт MUST отклонять Promise с `TypeError`. Повторный импорт MUST сохранять экземпляр, live bindings, асинхронный порядок инициализации и обработку ошибок подготовленного модуля.

#### Scenario: Type error in dynamically loaded source
- **WHEN** модуль, предназначенный для динамического импорта, содержит ошибку типов и включается в подготовку строковым импортом или `ModuleRoots`
- **THEN** ошибка возвращается на этапе `Check`/`Compile`, исполняемая программа отсутствует и пользовательский код графа не выполняется

#### Scenario: Prepared computed target
- **WHEN** вычисляемый specifier разрешается в модуль из подготовленного набора
- **THEN** импорт возвращает Promise namespace этого модуля и выполняет только необходимую инициализацию

#### Scenario: Unknown target
- **WHEN** вычисляемый specifier не разрешается в подготовленный модуль, в том числе для отсутствующего host-модуля или `data:` URL
- **THEN** Promise отклоняется с `TypeError`, resolver не вызывается и новый код не создаётся

#### Scenario: Repeated dynamic import
- **WHEN** один канонический модуль повторно или конкурентно импортируется в том же runtime
- **THEN** используется тот же экземпляр модуля и инициализация не повторяется

#### Scenario: Static and dynamic identity
- **WHEN** модуль доступен одновременно через статический и динамический импорты
- **THEN** они наблюдают общие live bindings и один namespace соответствующего канонического модуля

#### Scenario: Cached loader cannot delegate another program's permissions
- **WHEN** программа пытается переиспользовать уже загруженный модуль с тем же исходником, но другим разрешённым набором импортов
- **THEN** несовместимость обнаруживается до её пользовательских инициализаторов, а кешированная функция не предоставляет права импортов предыдущей программы

#### Scenario: Preserved import protocols
- **WHEN** подготовленный модуль использует top-level await, допустимые import attributes, CommonJS interoperability или deferred evaluation
- **THEN** соответствующие проверки, порядок promise jobs и протоколы выполнения сохраняются без компиляции во время импорта

### Requirement: Host implementation availability
Объявления внешних модулей MUST быть доступны отдельно от реализации для проверки проекта. До выполнения любого пользовательского кода программы runtime MUST требовать совместимые реализации всех host-модулей её подготовленного графа, включая разрешённые динамические цели. Модули, только зарегистрированные в окружении и не включённые в граф, MUST NOT становиться доступными динамическому импорту автоматически.

#### Scenario: Ambient declaration without binding
- **WHEN** проект содержит `.d.ts` для внешнего модуля и проходит проверку, но приложение не зарегистрировало реализацию
- **THEN** компиляция может завершиться успешно, а запуск отклоняется с указанием отсутствующего host-модуля до выполнения графа

#### Scenario: Dynamically selectable host module
- **WHEN** host-модуль разрешён строковым динамическим импортом или `ModuleRoots`, а его реализация отсутствует
- **THEN** запуск отклоняется до пользовательских инициализаторов, даже если конкретный запуск не выбрал бы этот модуль

#### Scenario: Registered but not prepared
- **WHEN** окружение содержит дополнительный host-модуль, который не включён в подготовленный граф
- **THEN** вычисляемый `import()` не предоставляет его экспорты

### Requirement: Referenced project source identities
При явной виртуальной конфигурации система MUST разрешать применимые project-reference redirects от ожидаемых declaration outputs к предоставленным TS-исходникам во время подготовки. Checker, execution graph и подготовленные динамические разрешения MUST использовать одну исходную идентичность без предварительной записи outputs и без подмены TS-модуля host-привязкой.

#### Scenario: Execute a referenced source without outputs
- **WHEN** приложение импортирует ожидаемый output referenced проекта, а каталог содержит только configs и TS-исходники
- **THEN** `Check` принимает корректный граф, `Compile` создаёт программу, runtime исполняет соответствующий TS-модуль и не требует host-реализацию отсутствующего output

#### Scenario: Error in a redirected source
- **WHEN** referenced TS-исходник содержит ошибку типов
- **THEN** `Check` и `Compile` возвращают ошибку с исходным TS-именем и диапазоном до выполнения кода

#### Scenario: Computed referenced import
- **WHEN** вычисляемый импорт выбирает подготовленный referenced модуль через допустимый output-style alias
- **THEN** runtime использует уже подготовленный TS-модуль и не возобновляет анализ referenced проекта
