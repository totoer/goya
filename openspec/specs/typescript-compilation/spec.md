# typescript-compilation Specification

## Purpose

Определяет проверку и компиляцию TypeScript до исполнения, доступную Go-приложению независимо от создания runtime и согласованную с поддерживаемым стабильным релизом языка.

## Requirements

### Requirement: Stable TypeScript compatibility
Каждый релиз интерпретатора MUST объявлять точную поддерживаемую стабильную версию TypeScript. При выпуске новой версии интерпретатора SHALL выбираться последняя стабильная версия языка; компилятор и стандартные объявления MUST соответствовать ей. Бета-версии и nightly MUST NOT выбираться автоматически.

#### Scenario: Reproducible language version
- **WHEN** приложение запрашивает сведения о версии компилятора или повторяет компиляцию в том же релизе интерпретатора
- **THEN** получает одну точную версию TypeScript и одинаковые правила языка без загрузки обновлений из сети

#### Scenario: Stable language update
- **WHEN** интерпретатор обновляет поддерживаемый стабильный TypeScript
- **THEN** вместе обновляются объявления стандартной библиотеки и проверки совместимости, а версия доступна приложению

### Requirement: Complete language analysis
Компилятор MUST поддерживать полный синтаксис и систему типов объявленной версии TypeScript, включая TSX при заданной JSX-конфигурации. Типовые результаты MUST соответствовать эталонному компилятору при одинаковых входах. Дополнительные ограничения профиля исполнения без компиляции строк MUST сообщаться отдельно и согласованно в `Check` и `Compile`, без изменения upstream-кодов диагностик TypeScript.

#### Scenario: Advanced type checking
- **WHEN** проект использует generics, conditional и mapped types, template literal types, overloads и control-flow narrowing
- **THEN** проверка принимает и отклоняет программы по правилам объявленной версии TypeScript

#### Scenario: TSX source
- **WHEN** приложение предоставляет TSX-исходник, корректные JSX-настройки и объявления JSX API
- **THEN** компилятор проверяет JSX-выражения и типы свойств по правилам поддерживаемой версии

#### Scenario: Unsupported built-in source constructor
- **WHEN** исходник непосредственно вызывает встроенный `Function` или его однозначно разрешённый встроенный аналог для создания функции из строки
- **THEN** `Check` и `Compile` возвращают согласованную error-диагностику пространства `goya`, а исполняемая программа отсутствует

#### Scenario: Shadowed function name
- **WHEN** исходник вызывает пользовательскую функцию с именем `Function`, не связанную со встроенным конструктором
- **THEN** ограничение встроенного конструктора не применяется по одному лишь написанию имени

### Requirement: Independent type checking
Система SHALL предоставлять публичную операцию `Check`, принимающую исходники проекта, настройки и окружение типов. Она MUST возвращать диагностики без выполнения пользовательского кода и Go API и без создания исполняемой программы.

#### Scenario: Check without runtime
- **WHEN** Go-приложение проверяет проект без создания runtime
- **THEN** получает результат проверки типов и не наблюдает вызовов зарегистрированных функций или побочных эффектов TS-модулей

### Requirement: Mandatory compilation gate
`Compile` MUST выполнять ту же проверку, что и `Check`, для одного снимка проекта. Любая диагностика уровня error MUST блокировать создание исполняемой программы, включая ошибки конфигурации, синтаксиса, типов и разрешения модулей. Отключение проверки через настройки MUST быть отклонено.

#### Scenario: Incompatible assignment
- **WHEN** компилируется `const count: number = "hello";`
- **THEN** возвращается ошибка типов с указанием исходника, а исполняемая программа отсутствует

#### Scenario: Error in dependency
- **WHEN** точка входа корректна, но статически импортированный TS-модуль содержит ошибку типов
- **THEN** компиляция всего проекта завершается ошибкой до выполнения любого его модуля

#### Scenario: Attempt to skip checking
- **WHEN** приложение передаёт настройки, отключающие проверку проекта или его объявлений
- **THEN** компилятор отклоняет такую конфигурацию и не создаёт исполняемый результат

### Requirement: Strict checking defaults
По умолчанию система SHALL использовать семейство проверок `strict` поддерживаемой версии TypeScript. Явные настройки MUST обрабатываться одинаково в `Check` и `Compile`; они MUST NOT отключать обязательный этап проверки.

#### Scenario: Missing parameter type
- **WHEN** без изменения настроек проверяется функция `function double(x) { return x * 2; }`
- **THEN** выдаётся ошибка implicit any в соответствии с эталонным strict-режимом

#### Scenario: Explicitly permitted dynamic type
- **WHEN** программа использует допустимый явный `any` или type assertion
- **THEN** checker применяет правила TypeScript, не обещая обнаружить ошибки, которые эти правила допускают

### Requirement: Structured source diagnostics
Диагностики MUST содержать severity, код, сообщение, исходное имя файла и диапазон позиции, когда он существует, а также связанные позиции при наличии. Диагностики TypeScript SHALL сохранять upstream-коды; ошибки интеграции SHALL иметь отдельное пространство кодов.

#### Scenario: Host call type error
- **WHEN** функция объявлена как `add(a: number, b: number): number`, а исходник вызывает `add("1", 2)`
- **THEN** диагностика указывает на аргумент в исходном `.ts` файле и доступна Go-приложению без разбора форматированного текста

### Requirement: Checked compilation entry points
Любой публичный Go API, принимающий исполняемый исходник или AST, MUST проходить обязательную проверку перед генерацией программы. Скрипту MUST NOT предоставляться встроенный аналог этих API. Повторное использование результата MUST зависеть от исходников, настроек, версии языка, профиля, окружения типов и разделения стартовых и дополнительных модулей.

#### Scenario: Run source with an error
- **WHEN** операция выполнения исходника получает программу с ошибкой типов
- **THEN** возвращает диагностики до начала выполнения пользовательского кода

#### Scenario: Changed API after previous check
- **WHEN** сигнатура Go API изменена после успешного `Check`
- **THEN** компиляция использует новое окружение и не принимает прежний результат проверки как актуальный

#### Scenario: Changed prepared module set
- **WHEN** при неизменных исходниках приложение меняет `ModuleRoots`
- **THEN** новая программа учитывает новый разрешённый набор, а прежний результат подготовки не используется как эквивалентный

### Requirement: Explicit virtual project configuration
`Project` SHALL принимать необязательный `ConfigFile`, указывающий на конфигурацию в предоставленном виртуальном каталоге. `Check`/`Compile` MUST согласованно учитывать её `extends`, references и настройки; явные host options MUST иметь приоритет. Пустой `ConfigFile` MUST сохранять прежний выбор исходников и настроек без автоматического поиска конфигурации.

#### Scenario: Configuration entirely in memory
- **WHEN** приложение передаёт `ConfigFile`, конфигурацию, её зависимости и TS-исходники из памяти
- **THEN** проверка и компиляция используют этот config graph без OS-чтения и без генерации build artifacts

#### Scenario: Explicit options override configuration
- **WHEN** конфигурация отключает strict, а приложение явно включает strict в options
- **THEN** редактор, `Check` и `Compile` используют strict и сообщают согласованные ошибки

#### Scenario: Existing calls preserve behavior
- **WHEN** приложение оставляет `ConfigFile` пустым, а каталог содержит неиспользуемый `tsconfig.json`
- **THEN** `Check`/`Compile` используют прежние правила roots/options и не начинают автоматически применять этот config

### Requirement: Configured analysis identity
Идентичность анализа MUST учитывать выбранный виртуальный config и содержимое его графа вместе с исходниками, options, версией языка и Environment. Ошибка конфигурации или referenced source MUST блокировать создание исполняемой программы; изменение графа MUST инвалидировать прежние результаты.

#### Scenario: Changed inherited configuration
- **WHEN** после успешного анализа содержимое inherited config меняет применимые настройки
- **THEN** новый анализ применяет новые настройки и не использует несовместимый кешированный результат

### Requirement: Additional prepared module roots
`Project.ModuleRoots` SHALL задавать дополнительные виртуальные пути исполняемых модулей либо имена host-модулей. `Check` и `Compile` MUST проверить их графы в общем снимке. Это поле MUST NOT само добавлять модули в стартовые точки. Неразрешимый или declaration-only source root MUST давать error-диагностику; одни объявления host-модуля SHALL допускаться для последующей проверки реализации при запуске.

#### Scenario: Computed import candidates
- **WHEN** приложение явно задаёт `/main.ts` в `EntryPoints`, а `/plugins/fast.ts` и `/plugins/safe.ts` в `ModuleRoots`
- **THEN** обе реализации и их зависимости проверены и подготовлены, но запуск программы сам по себе не выполняет их инициализаторы

#### Scenario: Invalid candidate is not silently deferred
- **WHEN** дополнительный модуль или его зависимость содержит ошибку типов, даже если скрипт никогда не выбирает этот модуль
- **THEN** `Check` и `Compile` сообщают ошибку до выполнения программы

#### Scenario: Explicit entry also listed as a module root
- **WHEN** модуль одновременно выбран стартовой точкой и указан в `ModuleRoots`
- **THEN** он выполняется по правилам стартовых точек и не создаётся второй экземпляр

#### Scenario: Declaration-only host candidate
- **WHEN** `ModuleRoots` содержит имя объявленного host-модуля без зарегистрированной реализации
- **THEN** проверка может завершиться успешно, а программа сохраняет требование реализации для проверки перед запуском

### Requirement: Immutable prepared program
Результат `Compile` MUST содержать неизменяемые исполняемые модули, разрешения импортов и требования окружения одного снимка. Изменения входных map, resolver, конфигурации или регистраций после компиляции MUST NOT менять эту программу. Замена кода или расширение разрешённого набора MUST требовать новой компиляции со стороны Go-приложения.

#### Scenario: Resolver changes after compilation
- **WHEN** после успешного `Compile` resolver начинает возвращать другую версию модуля или новый модуль
- **THEN** уже созданная программа использует прежний подготовленный код, а новый модуль не становится доступен

#### Scenario: Separate runtime instances
- **WHEN** один подготовленный `Program` запускается в двух совместимых runtime
- **THEN** код и правила разрешения одинаковы, а изменяемое состояние и экземпляры модулей разделены
